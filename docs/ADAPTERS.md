# Adapters: which coding agents the Companion can see and answer

The Companion started with Claude Code. Companion 0.2.0 added more agents through **adapters**: one small module per tool. This page says, per tool, what is read, what can be answered from the phone, and how safe the route is. The rules below hold for every adapter. **Companion 0.3.0 adds remote control** (prompts, stop, questions, start, live tail) for Claude Code and OpenCode only, behind the owner's switch, a per-device scope and a step-up: see [PROTOCOL3.md](PROTOCOL3.md) and, per tool, the Claude Code and OpenCode sections here. Codex, Muse, Herdr, agy and Ninox have no control route and none is typed into a terminal.

## Rules every adapter follows

1. **An adapter observes and delivers; the companion decides.** All checks (paused, rate limits, the paired device, the request fingerprint `bind`, local confirmation, expiry) happen in the companion's host. An adapter cannot answer anything by itself.
2. **The answer vocabulary is closed and has no scope.** The only things an adapter can be asked to deliver are: allow this one request, deny it (optionally with one of your own preset sentences as the reason), or send one of your preset sentences / one of the options the tool itself offered. There is no "always allow", "for this session", "change the policy", key name or command in the type, so no adapter can send one. (Free-text prompts exist since 0.3.0, but they are a different, separate interface, `ControlAdapter`, which the companion's host calls only after its own scope, step-up, limit and bind checks and only for adapters that declare it; the approval path above still has no free text.) A test (`adapters.lint.test.ts`) checks that no adapter source names such a decision.
3. **Fail toward the tool's own dialog.** A timeout, a mismatch, an unknown tool version, a crash or a closed connection all mean "no decision": the tool shows its normal question on your computer. The Companion never approves by waiting.
4. **An approval is called "applied" only when the tool says so.** After an allow is delivered the companion waits briefly for the tool's own follow-up (for example Codex's tool-finished event). If it does not come, the phone is told **sent**, not applied.
5. **Answering is version-gated.** Reading works on any version; answering is enabled only on tool versions the Companion was tested with (`botwarren-companion adapters explain <id>`). On any other version the phone shows the request and says "Answer on your computer".
6. **Sessions that cannot be gated say so.** An agent running without approval prompts shows the note "No approval prompts" and never offers Approve.
7. **Text read off a terminal screen is labelled** ("From the terminal screen") and is never answerable.
8. **Adapters have no network access.** They run inside the companion on your computer, reach only the tool's own hook calls, loopback services and fixed command lines, and put content only into the existing sealed (end-to-end encrypted) frames after masking. The relay and website see only ciphertext, exactly as before. `adapters.lint.test.ts` fails if adapter code imports a network or process module.
9. **You turn them on.** Hook-based tools need a hook installed in the tool, by a command you run (`botwarren-companion <tool> install-hooks`), which shows the change first, needs `--yes` when no terminal is attached, writes a backup, and edits only entries carrying its own marker (never Herdr's or yours). Tools that read a local service or a screen (Herdr, OpenCode, agy, Ninox) are off until you run `botwarren-companion adapters enable <id>`.

Commands: `botwarren-companion adapters` (what is known and on), `adapters explain <id>` (what it reads), `adapters enable|disable <id>`, `adapters hold <tool> away|never [seconds]`, `away on [--for 2h] | off`.

## Codex (companion 0.2.0)

- **Route:** Codex's synchronous `PermissionRequest` hook. Safety B: the request is identified by session, turn, tool and command, one-shot, and nothing wider than "once" exists in the hook's answer.
- **What it reads:** the hook events Codex sends (session start/end, that a prompt was submitted but not its text, the command or the file names of a patch for a permission request, that a tool finished but not its output, and the agent's last message when a turn ends). It opens no file. A patch's body (source code) is never sent: only the file names.
- **Detect / read:** every Codex session in your hook-enabled Codex shows on the phone as "waiting for you" with the command and hints (Outside the project, Network, Destructive, Protected file, Unknown tool). Without anything else this is read-only: **Answer on your computer**.
- **Approve / deny / "Deny and say":** only while you are **away** (`botwarren-companion away on --for 2h`) and Codex is set to hold (`adapters hold codex away`). Codex runs the hook *before* it shows its own question (observed; the question appeared only after an 8-second hook returned), so a held hook delays that question. The Companion therefore holds for at most 45 seconds, only while you said you are away, only on a tested Codex version, and then lets Codex ask on your computer as usual. Deny can carry one of your own preset sentences ("No, do not do that."); the model sees it as the reason.
- **Trust:** Codex runs only hooks you reviewed. After `codex install-hooks` open Codex and run `/hooks`. A changed hook must be trusted again, so the installed hook definitions never depend on settings you can change (the hold time is not in the hook file). `botwarren-companion codex doctor` asks Codex which of our hooks are trusted.
- **Tested with:** Codex 0.162.x. Verified on a real Codex 0.162.1 TUI: allow from a phone runs the command without a question, deny shows "Blocked by hook" and nothing runs, an unanswered hold falls back to Codex's own question, a hook that times out falls back too, and hooks still fire (before the reviewer) under `--approve-for-me`.
- **Limits:** questions the model asks you (`request_user_input`) and idle prompts cannot be answered from the phone; they show as waiting. A "don't ask again" choice (a persistent rule) can never be sent from the phone.

## Herdr (companion 0.2.0, read only)

- **Route:** Herdr's local socket, methods `ping`, `agent.list` and (only with `screenPreview`) `agent.read` on a blocked pane. Safety A for reading. **Nothing can be typed into a pane**: the client has no `send_keys`, `prompt`, `pane.*`, `run` or `start` method (an allowlist enforced in code and tested against a fake socket). Keystroke answers are not built (owner decision: not in v1).
- **What it gives you:** a "waiting" card on the phone for every agent Herdr recognises as blocked on an approval or question (Cursor, Aider, Cline, Antigravity and the rest, as well as Claude Code, Codex and Muse), with the folder name, marked **Answer on your computer**. A Herdr pane that is the same session as a hook-reported one (same session id) merges into that card and never replaces its structured request.
- **What it never sends:** the pane title (Herdr titles hold private task text). Screen text is off by default; `botwarren-companion adapters preview herdr on` shows up to 12 masked lines of a blocked pane, labelled "From the terminal screen".
- **Off until you enable it:** `botwarren-companion adapters enable herdr`. Unix only: Herdr's Windows pipe name is not documented and is not guessed.
- **Tested with:** Herdr 0.9.1 (protocol 22), including against a REAL Herdr server in the test lab: it recognised a real Codex (idle) and a real Muse showing its workspace-trust question (`blocked` about 3.5 seconds after the process started); our adapter read `agent.list` and, with `screenPreview`, the `detection` excerpt of the blocked pane, and the phone showed the card marked "from the terminal screen" and not answerable. The `detection` excerpt starts with the shell line that launched the agent, so it can contain a folder path: that is one more reason `screenPreview` is off by default.

## Muse (companion 0.2.0)

- **Route:** a plugin this companion generates (`botwarren-companion muse install-hooks`), installed with Muse's own `muse plugins install` and trusted by **you** with `muse plugins approve botwarren-companion` (trusting a plugin is Muse's gate). The plugin is only a manifest: each hook is a command that runs your companion; a changed hook must be approved again, so the plugin never changes with a setting. Safety B.
- **What it reads:** the hook events Muse sends (session start and end, that a prompt was submitted but not its text, the command or file a permission request names and Muse's own description of it, that a tool finished but not its output, Muse's own "waiting for approval" notification, the agent's last message when a turn ends). No file is read.
- **What you can do from the phone: deny, never approve.** Verified on a real, logged-in Muse Code 1.4.9 (lab): a hook **deny** works (Muse shows the block within a second, the command does not run, the model is told your reason); a hook **allow does not approve** the requests that really wait for a person (Muse kept its own approval dialog and did not run the command: "a hook-supplied confirmation is not approval"). So the phone offers **Deny** and **Deny and say**, and says "approve it on your computer". Denying is the safe direction.
- **What is held:** Muse sends `PermissionRequest` for every call it evaluates and resolves most within milliseconds, so only a request Muse marks as needing a person (an escalated command) is held, and only while you are away (`away on`) and Muse is set to hold (`adapters hold muse away`), at most 45 s, then Muse's own question shows. Everything else is reported and not held.
- **Version-pinned:** answering is enabled only on the version verified (1.4.9). Muse updates itself; on any other version requests show as "Answer on your computer" until you run the live checklist (`botwarren-companion muse doctor`) and `adapters verify muse <version>`.
- **Limits:** idle replies and questions are not answerable from the phone; Muse's own helper tool events are ignored.

## Claude Code (remote control since companion 0.3.0)

- **Route:** Claude Code Channels (research preview) for prompts, hooks for the rest. Needs Claude Code 2.1.234 or later, a **claude.ai login** (Channels are unavailable on an API key or a redirected base URL: a prompt is then reported `sent`, never `applied`), the session started with the channel flag, and on Team or Enterprise the organisation's `channelsEnabled`.
- **Prompt:** free text from a `control` device arrives as a `<channel source="botwarren-companion" kind="prompt" ...>` event, after a line naming the device. A busy session takes it at its next tool boundary or turn; an idle one starts a turn. A session without a connected channel is refused as unsupported.
- **Stop is soft:** the opt-in `PreToolUse` hook (`botwarren-companion claude install-hooks --control`) ends the turn at the session's **next tool call**. Text the model is generating and a tool that is already running are not cut. It is offered only after a `PreToolUse` call was seen in that session.
- **Questions:** one single-select `AskUserQuestion` is held in the same hook (`--hold`, at most 45 s) and answered from the phone; several questions, multi-select, no hold or no device online: the terminal asks, as usual.
- **Live tail:** read from Claude Code's session transcript (its format is not a public contract; the parser skips what it does not know): assistant text, your prompts, one-line tool calls. Thinking blocks are skipped. Tool output only if you switch it on for the session.
- **Not supported:** starting a session (`start` is OpenCode only in 0.3.0). A session started with `--dangerously-skip-permissions` is observe-only unless you set `allowBypass`.
- **Tested with:** Claude Code 2.1.300 in an isolated lab: free text to an idle and a busy session, a soft stop that kept the next tool call from running, and an `AskUserQuestion` answered from a simulated phone.

## OpenCode (companion 0.2.0, v2 API; remote control since 0.3.0)

- **Route:** OpenCode's local HTTP server (loopback only). Safety A: a pending permission request has its own id and is answered by that exact id. The answer is built from two literal words, `once` and `reject` (with a reason of fixed words plus, for "Deny and say", one of your own presets): a persistent rule cannot be produced by this code, and a test checks every request body a fake server received. Just before answering, the request is fetched again by id and must be unchanged; after an allow, the request must be gone on the server before the phone is told "applied".
- **What it reads:** the sessions, the folder each works in (its name only), whether each is running, and any permission request or question waiting for you (the action, what it names, OpenCode's own message). Never titles, prompts, messages, diffs, shell or file routes.
- **Off until you enable it** (`adapters enable opencode`), on port 4096 unless you set `adapters opencode port <n>`. OpenCode v2 always wants an HTTP password: name the environment variable that holds it with `adapters opencode password-env <NAME>` (the value is read from the companion's own environment, never from a file, and sent only to a server that answered with OpenCode's own 401). Without it the adapter reads nothing.
- **Tested with:** OpenCode 2.0.x. Verified against a real `opencode serve` 2.0.21 in an isolated, empty-environment HOME (no model): approve resolved the exact request and saved no standing rule; deny rejected it; a second answer to the same id was refused by the server. A request raised by a real model run was not exercised (no model credentials may be used); it uses the same API.
- **Remote control (0.3.0):** with remote control on and a `control` device, OpenCode takes a free-text prompt (queued behind the current turn), a stop (the server's own interrupt; the phone says `applied` only when the session has left the active list), a one-line answer to a question form that has a single free-text field (anything else stays "answer on your computer"), the live tail, and a **session start** in a project from your launch table (`default`, asking before every tool, or `plan`; `acceptEdits` has no verified OpenCode meaning). Only these server routes are used; shell, command, terminal, file, config and credential routes are never called, and a test checks the request log. Verified against a real `opencode serve` 2.0.21 in an isolated test environment with the built-in free model.
- **Limits:** question forms with fixed choices are shown but not answerable from the phone; sessions started with `opencode --auto` have nothing to approve; a standalone TUI server that other clients cannot reach is not seen, so control needs the background service.

## agy, Antigravity CLI (companion 0.2.0, read only)

- **What you get:** the companion reports that `agy` is installed (`agy --version`) and `botwarren-companion adapters` / `adapters explain agy` say how a phone sees it. **Waiting cards for agy come from Herdr** (`adapters enable herdr`): Herdr recognises agy and reports "blocked", and the card says "Answer on your computer".
- **Why it cannot be answered here:** agy's hooks fire per tool call, not per permission prompt, and a hook's allow is reported to be ignored in agy's default review mode, so there is no supported per-prompt route (the alternative, keystrokes, is not built). For a phone-side answer use **Google's own `agy remote-control`**. It goes through Google's cloud, so it is **not end-to-end encrypted by Botwarren**; the Companion only points to it.
- **Nothing is installed in agy and no file is read.** A hook installer for agy's `hooks.json` and the question "does a hook's allow skip agy's prompt" (spike S-A1) need a Google login that an isolated test must not use; both are left as next work.

## Ninox (companion 0.2.0, read only, forever)

- **Route:** Ninox's local server, one request: `GET /api/v1/sessions` on 127.0.0.1 (port 8080 or `adapters ninox`'s port). The shape is verified first (port 8080 is shared by many tools); Ninox's terminal, diff, delete, orchestrator and brain routes are never called, and the code cannot call them (the allowlist is one path).
- **What the phone shows:** Ninox **workers** with the note **"No approval prompts"**: Ninox starts workers with approval prompts bypassed, so there is nothing to approve, and nothing here can steer them. An **orchestrator** is an ordinary Claude Code session, so it appears as Claude Code's own card (same session id) with its normal approvals.
- **Never kept:** Ninox's names, repos, summaries, notes, costs and pull-request numbers.
- **Tested with:** a fake server in the shape read from Ninox's source at v0.34.0. Ninox is not installed on the test machine, so this is **not verified against a live Ninox**. Off until `adapters enable ninox`.
- The same note ("No approval prompts") now appears for **any** Claude Code session started with `--dangerously-skip-permissions` (its hook says so), and for Codex and Muse sessions that say they bypass approvals.

## Copilot CLI and the rest (next, not built)

- **GitHub Copilot CLI** has a `permissionRequest` hook that fires before its permission dialog and can allow or deny. Its documented answer is the flat `{"behavior":"allow"|"deny","message"?}` (not Claude's and Codex's `hookSpecificOutput`: an earlier note was wrong), exit code 2 denies, a timeout is fail-open. The documentation does not give the hook's input fields, and there is no Copilot on the test machine, so it was not built: it would be a descriptor on the same hook-family module once a real input and a live run are recorded.
- **Cursor, Aider, Gemini CLI, Cline and others:** waiting cards through Herdr only, read only. No hook is installed in them (Cursor's hooks fail open on malformed output, which makes a gate unsafe).
